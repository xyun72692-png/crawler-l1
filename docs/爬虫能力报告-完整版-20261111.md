## 一、一句话总览

**这套东西干的事**：去一个公开网站，把「列表页 → 详情页 → 附件」里的内容抄下来，去掉重复的，整理成一张能直接用的 Excel 表，最后告诉你"这次抄得怎么样、哪里没抄到、为什么"。

**它的脾气**：慢、老实、爱报告。宁可少抓几条，也不硬闯。

**它不是**：万能爬虫。要登录的、有验证码的、内容靠浏览器现算的、视频流——都做不到；境外站要**依赖系统层 VPN**，且线路决定成败。第 4 章逐条列了。

## 二、它到底怎么干活（打比方 + 真实流水线）

打个比方：派一个实习生去图书馆抄资料。

1. 先看门口的告示牌（`robots.txt`）——人家写了"这几排不许动"，他就不动
2. 进目录厅（列表页）——把每条资料的标题、编号、详情页位置记在本子上
3. 去书架取每一本（详情页）——把需要的字段抄下来
4. 顺手复印附件（PDF / Word / Excel / 压缩包）——还要核对"这真的是 PDF 吗"
5. 回工位整理——去掉重复的、清格式、排好序
6. 写工作总结——这次抄了几本、哪几本没抄到、为什么没抄到

对应到代码里，一次完整运行是这么 7 步：

| 步骤 | 代码里在干什么 | 失败会怎样 |
|---|---|---|
| 1. 开工检查 | 先看这个站有没有"冷却记录"（上次被封过还在封禁期？） | 冷却期内直接退出，**一个请求都不发** |
| 2. 读告示牌 | 请求 `/robots.txt`，记住哪些路径不许碰 | 404 = 没设限（放行）；401/403 = 明确拒绝，整轮停下 |
| 3. 建身份 | 开一个"会话"（Session），带上浏览器标识、Accept、Referer | 整个任务复用同一个会话，cookie 连着 |
| 4. 逐页抓列表 | 按配置的翻页方式一页页取，解析出每条记录的字段 | 某页 0 条 → 触发"复核机制"（见 6.2） |
| 5. 逐条抓详情 | 对没抓过详情、没抓过的记录，一条条请求详情页 | 失败按类型决定"下次补"还是"永久放弃" |
| 6. 下载附件 | 校验 robots → 校验是不是内网地址 → 下载 → 校验文件类型 → 存盘算哈希 | 超限/类型不符/被禁 → 只记链接，不落盘 |
| 7. 收尾 | 写数据文件、写报告（成功/部分成功/失败 + 原因 + 证据） | 报告是唯一可信的真相来源 |

**关键设计**：每一步的"失败"都分类型处理，不是一刀切重试。比如附件 404 了就一直重试是浪费，而网络超时值得重试——这套分类见第 6 章。

## 三、能力上限：它能做到什么程度

### 3.1 能抓的站点类型（四层 × 三态标注）

**三态定义**（全报告通用，禁止混用）：

| 标记 | 含义 | 判定依据 |
|---|---|---|
| **✅ 真实站验过** | 在真实站点跑出数据，报告可查 | `out\reports\` 里有对应 job 的成功报告 |
| **⚠️ 仅假站验过** | 代码+测试都有，真实站未接 | 只有 `tests\mock_site.py` 的用例 |
| **❌ 未支持** | 没有实现，或明确不做 | 代码里搜不到路径 |

| 层级 | 特征 | 怎么打 | 实例 | 状态 |
|---|---|---|---|---|
| **第 0 层：服务端渲染** | 源码里就有完整内容 | 直接抓 HTML 解析 | 温州人才网、乐清人才网、食品伙伴网 | **✅ 真实站验过** |
| **第 1 层：后台接口** | 源码里有 `/api/...`、`fetch(`、`.json` | 找到接口直接要 JSON | 暂无真实接入案例 | **⚠️ 仅假站验过**（`json` 模式 + 游标 + 业务错误码，用例 93–96 等） |
| **第 2 层：页面内嵌 JSON** | `<script id="__NEXT_DATA__">` 这类 | 从 script 抠 JSON | 暂无真实接入案例 | **⚠️ 仅假站验过**（用例 94） |
| **第 3 层：纯前端渲染** | 源码空壳，要跑 JS | 独立工具 `tools/fetch_rendered.py`；**主引擎未接** | 名言练习站 JS 页（渲染后 10 条 / 未渲染 0 条）、苍南人才网列表（1139 字节空壳） | **⚠️ 工具级验过，引擎未接** |

第 4 层（APP / 小程序 / 签名参数逆向）与第 5 层（指纹对抗、代理池）**明确不做**，理由见第十二章。

有个工具 `tests\probe_spa.py <网址>`，跑一次就能判断目标站属于第几层、robots 允不允许。

### 3.2 能抓的内容

- **文字字段**：标题、日期、编号、发布单位、金额、状态……要哪些在配置里写清楚（列名随你定）
- **详情页字段**：列表页没有的信息，点进去再抓
- **附件文件**：PDF / Word / Excel / 压缩包 / 图片，能下载并校验"是不是真的这个格式"
- **翻页方式**：三种都支持——数字页码（`?page=2`）、下一页链接（"下一页"按钮）、游标翻页（接口给个 next 值）
- **字段的多少取决于站点给不给**：列表页带 18 个字段（wzrc）和只带标题+日期（foodlaw）是两种命，缺的字段只能靠详情页补，补不到就留空——**不编造**

## 四、能力下限：现在做不到的（明确清单）

这一章是"丑话说在前面"，每条都写清为什么、有没有别的路。

### 4.1 完全做不到的

| 做不到 | 为什么 | 有没有别的路 |
|---|---|---|
| **需要登录才能看的内容** | 我没有你的账号身份 | 你把浏览器里的 Cookie 给我，就能用"你的身份"抓（技术上可行，需要你配合） |
| **图形验证码 / 滑块验证** | 破解要和站点长期对抗，投入产出极差，而且容易被封号 | 人工过一次验证后复用 Cookie；或找官方开放接口 |
| **字体加密的数字**（价格、电话被做成乱码字符） | 页面显示的是特殊字体，要解析字体文件才能还原成数字 | 改成抓后台接口；或单独立项做字体映射表（工作量大） |
| **带签名/时间戳的下载链接** | 链接是 JS 现算出来的，源码里没有 | 渲染后链接在 DOM 里，但要逐条提取；v10 只存 HTML |
| **视频/音频流（m3u8 分片）** | 要把几十上百个小分片拼成一个文件，现在没做 | 只支持直链 mp4/mp3 |
| **音视频内容理解（转文字）** | 没有语音识别能力 | 不提供 |
| **境外站点** | 引擎无代理能力；直连时 google/duckduckgo 全超时 | **系统层 VPN 换出口**（2026-11-15 实测 WARP 可用）；可达性取决于线路 |
| **高频 / 并发抓取** | **故意不做**。理由：实测约束是**单位时间密度**——约 9 次/分钟跑了 111 个请求没事，约 21 次/分钟累计约 150 个就被封；并发只会把密度拉爆 | 用"控密度（≤12 次/分钟）+ 分批 + 单任务 ≤200 请求"代替 |

> **注**：本表已移除「纯前端渲染的站」——v10 起由独立工具 `tools/fetch_rendered.py` 支持（先探测 → 人决定 → 每页渲染一次；引擎仍未接）。
> 渲染成本高（一次导航带十几个子资源），只在确有必要时使用。
> **v13 修订（2026-11-14）**：不是所有"渲染站"都一样，要分三类——
> ① **有明文接口**（jpaas / 北森 / 大易）：plain 就能抓，**不需要渲染**；
> ② **纯前端无接口**：才需要渲染（v14 T2）；
> ③ **加密签名接口**（jrzp 的 `/zpapi/api` 带 AES/HMAC、宁波 `nbrcafter=md5(key+md5(ts))`）：**按红线不逆向**，这类才是真做不到。
> 换句话说：**"渲染"是最后手段，"找接口"永远先试。**



### 4.2 能抓但不能读的

| 东西 | 现状 |
|---|---|
| **PDF / Word / Excel 文档** | 能下载、能校验、能算哈希，但**读里面的文字**要靠另一套 Office 工具（能读 .docx/.xlsx/.pptx；老的 .doc/.xls 要先转换） |
| **图片** | 能下载，**不做文字识别（OCR）**——图片里的招聘电话、二维码内容读不出来 |
| **扫描件 PDF** | 本质是图片，同上，读不了里面的字 |

### 4.3 能抓但抓不全的（重要，容易被误判）

| 情况 | 会发生什么 | 怎么办 |
|---|---|---|
| 站点把"每页条数"写死成 5 条 | 只能一条条翻，请求数下不来（温州人才网就是这样，`pagesize=50` 实测无效） | 接受现实，改成分批 + 错峰 |
| 站点有 IP 级频率限制 | 抓多了会被"软封"（回正常状态码 + 空内容） | 见第 6 章 10 道防线 |
| 信息本身不全（站上就没填） | 抓回来是空的，不是抓失败 | 报告里区分"字段缺失"和"页面失败" |
| 筛选参数不精确（如"双休"筛出单双休） | 会混进不符合条件的 | 必须做二次校验（乐清那轮就踩过） |

## 六、风险防护：10 道防线

这一章是这套东西最值钱的部分。每条都说明"防的是什么、怎么触发、怎么验证"。

### 6.1 第一道：robots 检查（防"抓了人家不让抓的"）

- **规则**：404 = 没设限（放行）；200 = 按 Disallow 逐条判断；401/403 = 明确拒绝，整轮停
- **5xx / 超时**：等 1 秒重试一次，还失败就当"不许"，**绝不默认放行**
- **列表页、详情页、附件三处都查**，附件还按域名缓存规则
- **重要澄清**：robots 只管"哪些网址允许抓"，**不管"多久抓一次"**。robots 允许 ≠ 可以高频抓。限流是另一套机制（见 6.2）

### 6.2 第二道：软封检测 + canary 复核（防"被封了还在白抓"）

**这是上次吃过亏以后专门加的。**

**上次出了什么事**：抓温州人才网时，站方不是回"禁止访问"，而是回了一个"HTTP 200 + 3103 字节的空壳页"。程序看着状态码正常，以为"这页真没职位"，于是继续翻页——**被封之后 2.5 分钟里又发了 53 次请求**，等于自己把封禁时间往后推。

**现在的做法（canary 复核）**：

```
某页解析出 0 条
  ↓
先去抓一个"已知一定有内容"的对照页（canary，比如"双休第 1 页"）
  ↓
┌─ 对照页也没内容 → 判定被软封 → 立刻停手 + 写冷却记录 + 报告 failed/soft_block_suspected
└─ 对照页有内容   → 说明这页是真的空 → 照常继续（记 anomaly）
```

**为什么不用"字节数阈值"当判据**：站点换个模板就失效了，不可靠。用"对照页"是行为判据，更稳。

**报告里会留证据**：那一页多少字节、解析出几条、对照页多少字节、服务器标识是什么。

### 6.3 第三道：冷却期（防"封完了又去撞"）

- 判定被封 → 写一个记录文件：`_cooldown_<域名>.json`，标明"到几点之前别碰这个站"
- 下次开跑**第一件事**就是看这个文件
- 没过期 → **一个请求都不发**，直接退出，报告 `failed/cooldown_active`
- 冷却时间阶梯：2 小时 → 6 小时 → 24 小时（越撞越久）
- 到期自动恢复；文件坏了会"隔离坏文件 + 按 2 小时冷却处理"（宁可多等，不可误放）
- **同域名的子站共用一把锁**：温州人才网主站和两个乐清分站共用一个冷却记录——因为封禁按 IP 封，子站会一起遭殃

### 6.4 第四道：Retry-After（防"瞎等"）

- 站点回 429 并说"等 2 秒" → **真等 2 秒**（以前是自己瞎等 3 秒，不看站点说什么）
- 等待时间 = max(站点要求, 自己算的退避时间)
- 日志会写清是哪种来源（"Retry-After=2s" 还是"退避=3.0s"）

### 6.5 第五道：请求像人（防"一眼看出是机器人"）

| 项目 | 现状 |
|---|---|
| User-Agent | ⚠️ 伪装成普通浏览器 `Chrome/152.0.0.0 Safari/537.36`，**没有自报身份** | 头部由 identity.py 统一生成；三站 cffi 已对齐 TLS，其余 plain 站仍可能露 Python |
| Accept / Accept-Language / Connection | ✅ 有 |
| **Referer（我从哪一页过来的）** | ✅ 按页传：第 1 页→站点根，之后→上一页 |
| **整轮共用一个会话（cookie 连着）** | ✅ 有 |
| Sec-CH-UA / Sec-Fetch-*（新版浏览器指纹头） | ✅ **有**（identity.py 统一生成；三站 cffi） |
| 请求间隔加"长尾停顿"（模拟人看久一点） | ❌ **没做**，见第 9 章建议 |

### 6.6 第六道：SSRF 与内网防护（防"被恶意链接骗去访问内网"）

- 每个附件链接、**每一跳重定向**都检查：是不是内网地址、回环地址、局域网地址
- 检查两遍：字面判断 + DNS 解析后的真实 IP 判断
- DNS 解析失败 → **拒绝**（不放行，宁可抓不到）
- 重定向手动逐跳处理：**发请求之前**就校验，指向内网的那一跳根本不会发出去

**已实现的缺口**：不防 DNS rebinding（校验时是公网、实际连的时候变成内网）——要防得在 socket 层绑定已校验的 IP，工作量大，目前没做。

### 6.7 第七道：附件三重闸门（防"下了一堆垃圾"）

| 闸门 | 规则 |
|---|---|
| 数量 | 每条记录最多 5 个附件 |
| 单文件大小 | 最大 50MB |
| 任务总量 | 最大 500MB（**跨页累计**，不是每页重新算） |
| 类型白名单 | 只收指定扩展名（如 .pdf/.docx/.xlsx/.zip） |
| 文件头校验 | 下载后看前几个字节是不是真的 PDF/Office（防"改名成 .pdf 的 exe"） |
| 超限处理 | 只记链接，**不落盘**，状态标 `too_large` / `too_many` / `quota_exceeded` |

### 6.8 第八道：不覆盖、不删除、不静默失败

- 附件同名时自动退避成 `a_1.pdf`，**绝不覆盖**已有文件
- 数据文件原子写入（先写临时文件+刷盘，再一次性替换），断电不会写坏
- 任何"页失败 / 字段缺失 / 附件失败"都会进报告的 `anomalies`，**不许静默跳过**
- 空页不算成功（默认行为），防止"选择器写错了"被当成"这站没数据"

### 6.9 第九道防线：筛选条件指纹（防"换了条件还用旧断点"）

**它防的是什么**：同一个任务名（`--job`），你换了筛选条件（比如从"近 3 天"改成"近 7 天"、
或换了区县 / 薪资档 / 行业），程序如果还用上一次的断点，就会认为"这几页已经抓过了"——
于是**一个请求都不发**，报告还会写 `success`、覆盖率 1.0。这是最难发现的一种假成功。

**怎么防的**：
- 每次运行都给当前的 URL 算一个"指纹"（URL 里的筛选参数，去掉页码部分，取 sha1 前 12 位）
- 指纹和上次不一样 → 清空页码断点（含"下一页"模式的断点）、清掉旧的总页数记录，**保留去重键**
- 报告里会留一条 `anomalies`：`筛选条件变更 xxx→yyy，已清 pages_done/urls_done/next_url/pages_declared`

**为什么要保留去重键**：去重键是"这条数据抓过没有"，跟页码无关，清掉会导致重复抓同一批数据。

**覆盖情况**：数字分页和"下一页/游标"分页都已覆盖（用例 127/128 测数字分页，129/130 测下一页模式）。

| 场景 | 该有的行为 | 用例 |
|---|---|---|
| 同一任务换筛选（数字分页） | 旧断点作废，重新抓 3 页，coverage=1.0 | 127 ✅ |
| 同一任务同筛选（数字分页） | 断点保留，第二跑全跳过（noop） | 128 ✅ |
| 同一任务换筛选（下一页模式） | `urls_done`/`next_url` 一起清，重新抓，不留旧 URL | 129 ✅ |
| 同一任务同筛选（下一页模式） | 断点保留，第二跑不新增 | 130 ✅ |

### 6.10 第十道：请求闸门（v12 起，代码强制）

前九道里，"间隔随机"和"请求预算"原本靠操作纪律。v12 把它们变成引擎保证：

```python
# crawlers/gate.py
窗口        60 秒 / 12 次（滑动）
最小间隔    4.8 ~ 6.5 秒（随机抖动）
预算        ≤ 200 请求/任务
时长        ≤ 30 分钟/轮
钩子        Session.send()   # 挂 request() 会漏掉每一跳 302
报告        gate: {requests_used, actual_rpm, throttled, stopped_by, by_host}
```

- 超限抛 `GateStop`，`finalize` 记录对应 reason，**不会静默继续**
- 回环豁免只认测试环境（存在 `CRAWLER_TEST_TMP` / `CRAWLER_OUT_DIR` 等变量时）；
  生产即使目标是 127.0.0.1 也走闸门（`CRAWLER_GATE_FORCE=1` 可强制开启）
- 用例 **179–202** 覆盖：闸门速率/预算/时长/回环两模式/边界/默认值/Crawl-delay（179–189）；四阶段闸门穿透（190–193）；两段式与账目/doctor（194–201）；第 2 段附件失败（202）
**v12.1 补的两个数据安全坑**（闸门触发时"数据/状态不能丢"）：

- **附件**：预算耗尽时，已下载成功的附件必须保留 `status=ok` + `path` + `sha256`，只把没轮到的标 `skipped_budget`。
  修法是"先把全量条目写回 `row["attachments"]`（状态 `pending`），每完成一个就更新"，
  而不是"最后才赋值"——否则抛异常时已完成的结果全部丢失（用例 191：`ok==2 / pending==5`）。
- **canary**：撞上预算时要立即收尾并记 `reason=request_budget_exceeded`，
  不能退化成"普通软封判定"（用例 192：`requests_used==1` + `reason=预算`）。

## 九、建议往哪发展（按"一次性抓取"这个主场景重排）

**主场景已定**：**一次性抓一份「当前在招」的完整快照**，不是长期监控。
排序因此变了——先保证数据对，再保证请求预算，指纹类手段降到最后。

排序原则：**先修会出错的 → 再修更省请求的 → 最后才是更好看的**。

### 第 1 优先：数据正确性（这是唯一"错了就白干"的东西）

| 要做 | 为什么 | 工作量 |
|---|---|---|
| 总页数口径在**每个真实站**都跑一次 | 现在只有温州人才网验过（M=5→coverage=1.0）；其他站还没跑过带 `coverage` 的报告 | 每站 1 次跑 |
| `coverage < 1.0` 时必须能一眼看出来 | 一份"覆盖 60%"的快照，如果不看报告就当全量用，结论会错 | 已成（报告里有字段），要做的是**交付时主动说明** |
| 每次交付附上"这份数据覆盖了几成" | 同上 | 交付习惯 |

**为什么排第一**：一次性快照的价值全在"这份数据是否完整"。少抓了 40%，比被限流更严重——被限流你知道，少抓了你不知道。

### 第 2 优先：请求预算（一次性抓取的核心矛盾）

既然目标是一次性抓完，那就要在"请求数够用"和"不被封"之间找平衡：

1. **静态快照打法**：一次性全量跑完存档，之后静态条件可续跑补新。
   抓到的那份 jsonl 就是快照，不要反复重抓同一个站。
   ⚠️ 静态条件仍可用断点续跑；`settr=3` 这种**滚动时间窗**改走 v14.12.1 的 window 模式：
   每轮重抓前 `refresh_pages`（默认 3）页，靠 `seen_keys` 去重；`full` 与 `window` 不要混用。
2. **筛选分片**：按 `citycategory` / `settr` / `wage` 把大目标拆成小片，
   单片请求量小、可中断、可分批跑（今天跑乐清片，明天跑瑞安片）。
3. **明确写进流程**：完整快照用 `wzrc_all`；日常更新用 `wzrc_inc` 的 window 模式。

**实测依据**：上次被封是 **IP 级**限流，约 **21 次/分钟**、累计约 150 个请求后触发；而 2026-11-11 那批以约 **9 次/分钟**发了 111 个请求，全程未被限。解封后 UA 一个字节没改就正常返回
→ **请求头不是根因，请求总量才是**。所以省请求比伪装指纹有效得多。

### 第 3 优先：长尾停顿（定位为"观察项"，不是防线）

- 每翻 15~20 页插一次 8~20 秒停顿，保持 0.8~1.5 秒基线不变
- 模拟"人快速翻几页 → 停下来看一个职位 → 再翻"
- **但要说清楚**：这一条**没有任何验证证据**说它真能降低被限流的概率。
  它只是让流量形状更接近人，属于"成本几乎为零、赌它有用"的观察项。
  别把它当成"加了就不会被封"。

### 第 4 优先：全站统一 cffi（三站已完成，其余逐站评估）

- `identity.py` 已统一 UA / Sec-CH-UA / Sec-Fetch；`foodmate / wzrc_all / foodlaw` 三站已切 cffi，TLS 也对齐 Chrome
- 其余站仍走 plain（requests），仍是“头对、TLS 不对”的半套伪装；要切必须逐站跑 A/B，不能一刀切
- 但上次被封是**密度**的问题，不是**指纹**的问题——切 cffi 也挡不住“约 21 次/分钟”这种密度的封禁

### 第 5 优先：接 Playwright（2026-11-12 已做第 1 段：独立工具 `fetch_rendered.py`，引擎待接）

装了之后**可能**打开：政府站 JS 栏目、部分前端渲染站、任何"源码里有内容但页面要 JS 才显示"的站。

**不保证能用**：BOSS直聘 / 智联 / 51job 有额外反爬（签名参数、设备指纹、风控跳转），
装了浏览器也可能过不去——别把它当成"万能钥匙"。

**代价**：慢 5~10 倍、内存 150~300MB/页、浏览器版本要跟驱动对上。
**建议**：先只在"必须用它"的站上开，其他站继续走快速通道。

### 第 6 优先：字段质量的"规则库"（2~3 天）

现在薪资、学历、双休的解析规则是一站一套、写在清洗脚本里。抽出来做成可配置规则库：

- 薪资格式模式表（"8K~1.2万"、"1万~1.5万"、"面议"、"年薪80-100万"...）
- 学历码表（初中/高中/中技/中专/大专/本科/硕士/博士/不限）
- 岗位性质识别（保险销售 / 机构招生 / 配送骑手 / 企业直招）

**好处**：接新站时不用重新写规则，勾一勾就行。

### 第 7 优先：数据可视化（可选）

把抓到的数据做成简单的趋势图。一次性快照场景下用处不大，属于锦上添花。

### 可选能力：定时任务 + 变化提醒（**当前未配置**）

- 每天早 8 点自动跑增量（Windows 任务计划）
- 跑完比对"新增了哪些 / 哪些下架了"，有变化发到飞书/微信

**说明两件事**：
1. **现在没配**——所有任务都是手动跑，会话一结束后台进程就没了（与 8.3 一致）。
2. 这是**可选能力**，不是主场景。你的主场景是"一次性在招快照"，
   持续监控只在"想知道市场怎么变"时才需要，不必为此增加复杂度。

### 明确不建议做的

| 不建议 | 原因 |
|---|---|
| 多线程/并发抓取 | 实测约 21 次/分钟、累计约 150 个请求就被封；并发只会更快 |
| 破解验证码 | 长期对抗、投入产出极差、容易封号 |
| 代理池大规模轮换打同一个站 | 对公共站点不礼貌，且技术上迟早被识别 |
| 抓取需要登录才有权限的内容 | 越权，不做 |
| **靠换 IPv6 绕限流** | 本机没有可用 IPv6；且多数 WAF 按 /64 段限流，换地址不解决问题（未验证，不推荐） |

## 十、出问题怎么查（排查手册）

### 10.1 先看报告状态

报告在 `D:\agent-work\out\reports\report-<任务>-<时间>.json`，看 `status` 和 `reason` 两个字段：

| status / reason | 什么意思 | 该怎么办 |
|---|---|---|
| `success / ok` | 正常抓完 | 直接看 Excel |
| `noop / all_pages_already_done` | 所有页上次都抓完了 | 正常，不是出错 |
| `noop / nothing_done` | 本轮没有任何可做的事 | 正常 |
| `noop / rebuild_index_only` | 单独跑了 `--rebuild-index` | 正常，零网络 |
| `partial / empty_page_seen` | 有页面解析出 0 条 | ① 先确认不是被封（看有没有 canary 记录）② 检查选择器是不是站点改版了 |
| `partial / page_range_truncated` | 只抓了部分页（站点声明 M 页，你只抓了计划上限那么多页） | 想全量就调大页数上限；报告里的 `coverage` 会告诉你覆盖了几成 |
| `failed / soft_block_suspected` | **判定为被封** | 别重试，等冷却；看报告里的 `anomalies` 确认证据 |
| `failed / cooldown_active` | 还在冷却期（报告 `cooldown.reason` 会写原因） | 等时间到；急的话 `--ignore-cooldown` 强跑（不建议） |
| `failed / cooldown_active`（`cooldown.reason=cooldown_file_corrupt`） | 冷却文件坏了 → 按 2 小时伪冷却处理（fail-closed） | 程序已自动隔离坏文件；到期自动恢复，也可手工删掉那个文件 |
| `failed / robots_denied` | 站点明确不许抓 | 停下来，由你决定要不要继续 |
| `partial / detail_pending_remains` | 有些详情页还没抓到 | 再跑一次会自动补 |
| `failed / all_pages_failed` | 所有页都失败 | 网络问题或站点挂了，先手动打开网页看 |

### 10.2 常见现象对照表

| 现象 | 先查哪里 |
|---|---|
| 抓回来 0 条记录 | ① 选择器写错了（存一份原始 HTML 手看）② 是不是被软封了 |
| 详情页全失败 | ① 是不是要先访问列表页拿 cookie ② 是不是被 403 了（看 `abort_on` 配置） |
| 附件全 `robots_denied` | 那个附件目录真被 robots 禁了 → 只记链接，要不要抓由你定 |

### 11.1 目录结构

| 路径 | 装什么 |
|---|---|
| `data\raw\<任务>.jsonl` | 原始数据，一条一行（JSON 格式） |

### 11.2 每条记录的字段

**业务字段**（按站点不同）：标题、公司、薪资、学历、地区、发布时间、福利标签、详情链接……

**系统字段**（每条都有，用来追溯）：

| 字段 | 意思 |
|---|---|
| `source_url` | 这条数据从哪个网址来的 |
| `fetched_at` | 什么时候抓的 |
| `http_status` | 服务器返回的状态码 |
| `content_hash` | 内容指纹（内容变了指纹就变，用来判断"是不是同一条"） |

**这些字段的意义**：任何时候你都能回答"这条数据是真的吗、什么时候抓的、当时站上是不是这样"。

## 十二、边界与原则（我给自己定的规矩）

这几条不是技术限制，是**主动选择**：

| 原则 | 具体表现 | 为什么 |
|---|---|---|
| **不做并发** | 单线程，一次一个请求 | 实测约束是密度：约 9 次/分钟没事，约 21 次/分钟累计约 150 个就被封；公共站点经不起 |
| **慢一点** | 站点配置 0.8~5 秒；**实际间隔由请求闸门兜底到 4.8~6.5 秒** | 别把人家服务器压垮，也别被当成攻击；闸门保证一分钟 ≤12 次 |
| **先问许可** | 先读 robots，说不许就不抓 | 这是站点的明文告示 |
| **不删除** | 只移动/归档，不 `rm` | 删错了找不回来 |
| **不覆盖** | 同名文件自动退避成 `_1` | 同上 |
| **不静默失败** | 任何失败都进报告 | 不然你不知道少了什么 |
| **先演练** | 装软件默认 dry-run，加 `-Execute` 才真装 | 防手滑 |
| **公共站点优先保护** | 温州人才网这类政府下属站，宁可不抓完也不猛冲 | 找工作旺季，别影响真人使用 |

## 十三、合规边界：会不会被追踪？会不会有事？

这一章回答两个问题：**「对方能查到我吗」** 和 **「我做的事会不会出事」**。
先说结论：**这两件事不是一回事**，而且第二件才是真正要当心的。

### 13.1 技术上，对方能看到什么（我核过代码，不是猜的）

每次请求都会带出去这些：

| 信息 | 我们发的是什么 | 说明 |
|---|---|---|
| **IP 地址** | 你的宽带出口 IP | **必然暴露**。没有 IP 就收不到回包，这是 TCP 协议决定的 |
| **User-Agent** | `Chrome/152.0.0.0 Safari/537.36` | ⚠️ **伪装成浏览器，没有自报身份** |
| Accept / Accept-Language | 浏览器样式 | 正常 |
| **Referer** | 按页传（第 2 页的 Referer 是第 1 页） | 这条做得像人，是加分项 |
| Cookie | 每次运行新开，不跨运行保存 | 每次都是"新访客" |
| **请求间隔** | **4.8~6.5 秒**（闸门强制；站点配置只是下限来源） | 比真人还慢一点：一分钟最多 12 次 |
| **TLS 指纹** | **已对齐 Chrome**（`curl_cffi` impersonate `chrome152`，2026-11-14 启用） | ✅ foodmate / wzrc / foodlaw 三站已切 |
| 代理 | **引擎没有**（无 `proxies` 配置）；**系统层可切 VPN** | 单 IP 会话到底；换 IP 只能改系统出口 |

**当前状态：三个主力站已整体对齐，其余站仍是半套**

`foodmate / wzrc_all / foodlaw` 已切 `curl_cffi chrome152`，UA / Client Hints / TLS 同源；
其余仍走 plain 的站，依旧可能出现“UA 说 Chrome、TLS 像 Python”的矛盾。
**所以对外只说“主力三站已对齐”，不说“全线对齐”。**

**还有一件事要知道**：温州人才网那次限流，**站点的访问日志里已经记下了你的 IP、时间、访问过的每一个 URL**。
这类日志一般留存 3~6 个月。所以准确的说法是：**「没被追究」不等于「没留下痕迹」**。

### 13.2 「被查到」其实有三种意思，要分开看

| 层级 | 对方知道什么 | 现实情况 |
|---|---|---|
| ① 知道**有程序在抓** | 有个非人类的访问者 | **基本一定知道**：看请求间隔、Referer、TLS 指纹就能分辨 |
| ② 知道**是哪个 IP** | 你家/学校的出口 IP | **一定知道**，藏不了也不必藏 |
| ③ 知道**是哪个人** | 姓名、住址 | **要运营商配合才能拿到**，而且要走公安/法院的调证手续 |

现在处于 ① 和 ② 之间：站点知道有个爬虫、知道是哪个 IP。
③ 需要"有人专门去查你"，而这类事的经济成本远大于收益。

**为什么 ③ 很难发生**：
- 家宽 IP 是动态的，要运营商查 RADIUS/PPPoE 拨号日志才能对上时间
- 学校/公司网是 NAT 出口，内部还有一层日志
- 都得走正式调证手续

### 13.3 「会不会出事」看三个条件（这才是重点）

判断抓数据有没有事，法律上主要看三条。一条条对着我们现在的情况说：

**条件 1：数据是公开的吗？**
✅ **是**。招聘信息本来就给所有求职者看，你打开浏览器也能一条条看。不是"偷看别人的私密数据"。

**条件 2：有没有绕过技术保护措施？**
✅ **没有**。
- `robots.txt` 返回 404（站点没设限 = "没说不许"）
- 没有验证码
- 不需要登录
- 没有加密签名要破
- 而且引擎**遇到 robots 说"不许"就真的不抓**，遇到 401/403 就停

**条件 3：有没有造成损失或影响服务？**
✅ **没有实质影响**。闸门强制 4.8~6.5 秒一个请求、**一分钟最多 12 次**——比真人慢慢刷还慢（食品伙伴网 245 页实测 10.5~10.6 次/分）。
那次限流是站点**自己的保护机制**，不是"被攻击"。

**对照刑法第 285 条**（非法获取计算机信息系统数据罪）：核心是**"侵入"＋"技术手段"**。
抓一个谁都能看的公开页面，不构成"侵入"。

### 13.4 红线清单（这几条越界，性质就变了）

| 行为 | 风险 | 我们现在 |
|---|---|---|
| 抓公开列表 + 低频 + 不碰个人信息 | **很低** | ← 在这一档 |
| **破解验证码 / 绕过登录墙** | 明显上升：这就成了"突破技术措施" | ❌ 不做 |
| **高频到把站点打挂** | 可能构成"破坏计算机信息系统" | ❌ 不做（单线程 + 闸门 4.8~6.5 秒） |
| **抓简历库 / 身份证 / 手机号并汇总** | ⚠️ **风险最高**，碰《个人信息保护法》 | ❌ 不做（见 13.5） |
| 用代理池大规模轮换打同一个站 | 从"访问"变成"对抗" | ❌ 不做 |

### 13.5 个人信息这条线（真正需要警惕的地方）

这是整套东西里**唯一可能真出事**的入口，必须单独说。

招聘信息里可能夹着个人信息：
- 职位描述里的"联系电话 138xxxx"
- HR 的姓名、微信
- 企业联系人

这些一旦被抓下来**保存、汇总、传播**，性质就从"抓公开信息"变成"处理个人信息"——
受《个人信息保护法》管，是**民事赔偿 + 行政处罚**那一档，比"抓网页"严重得多。

**现在的做法是干净的**：交付的两份 Excel 字段是
职位 / 公司 / 薪资 / 学历 / 经验 / 地区 / 福利 / 发布时间 / 链接——
**没有手机号，没有 HR 姓名**。

**规矩**：职位属性（标题、公司、薪资、学历、地区、链接）随便抓；
**联系方式和个人身份信息不提取、不汇总、不保存**。

### 13.6 要不要"藏得更好"？（可选项，不是必须）

**已完成大半**（v14.1~14.3）：

| 项 | 状态 |
|---|---|
| `identity.py` 统一身份（UA / Client Hints 同源） | ✅ 已做 |
| `curl_cffi` TLS 冒充（chrome152） | ✅ 已做，三站已切 |
| stealth 补丁（19 项）+ 自检 6/6 | ✅ 已做 |
| 换出口 IP | ✅ 有手段（手机热点 / 系统 VPN），**引擎不接管** |
| 代理池轮换打同一站 | ❌ 不做（性质变对抗） |
| 行为模拟（鼠标/停留） | ❌ 不做 |

但要说清两句话：

1. **藏得好 ≠ 免责**。反过来说，**现在做的事本来就不需要藏**。
2. **半套伪装比诚实更糟**。真被问到，"我 UA 里写了是数据采集、也遵守了 robots"是解释；
   "我伪装成 Chrome"就没法解释了。

**如果想让姿态更干净**（建议但非必须）：
- 已完成：`identity.py` + 三站 cffi 已补 `Sec-CH-UA` / `Sec-Fetch-*` 并对齐 TLS；其余站按同样方式逐站切
- UA 里加一个诚实的标识 + 联系方式（机器人圈叫"善意爬虫"，站点看到通常会放行甚至提供接口）
- 想更保险就用手机热点跑（换 IP 成本最低）

**不建议**：
- 代理池轮换打同一个站（性质变了）
- 抓简历/个人联系方式（唯一真正高危的地方）

### 13.7 一句话

**「会不会被查到」**：站点知道有个爬虫、知道你的 IP —— 这个已经发生了，藏不住也不必藏。
**「会不会有事」**：只要不碰登录墙、不破验证码、不抓个人信息、不把站点打挂，
你做的事本质上就是「**用程序代替手指点了 500 次下一页**」，和真人刷招聘网站没有性质区别。

**真正的风险点不在"追踪"，在于哪天想"抓得更深"**——抓简历、破验证码、绕登录。
到那时候，"被查到"才会变成问题。

#### 16.2.1 浏览器指纹的三层结构（50% 覆盖率的来源）

"浏览器指纹"是笼统说法，实际分三层。我们的覆盖情况：

| 层级 | 检测项 | 我们 | 说明 |
|---|---|---|---|
| **基础层** | `navigator.webdriver` | ✅ | 真 Chrome 为 false；headless 默认 true |
| | `window.chrome` | ✅ | 真 Chrome 存在，部分自动化环境缺失 |
| | `navigator.plugins` | ✅ | 真浏览器有默认插件集，无头环境常为空 |
| | `navigator.languages` | ✅ | 必须与 `Accept-Language` 一致 |
| | `navigator.permissions` | ⚠️ 部分 | 无头环境下权限查询返回值有差异 |
| **特征层** | Canvas 指纹 | ✅ | 同机稳定；虚拟环境会漂移 |
| | WebGL 指纹 | ⚠️ 部分 | 无头模式常报 SwiftShader 等虚拟渲染器 |
| | Audio 指纹 | ⚠️ 部分 | 音频上下文处理存在细微差异 |
| | 时区 / 语言 / 屏幕 | ✅ | 本机真实值 |
| **行为层** | 鼠标轨迹 / 键盘节奏 / 停留滚动 | ❌ | **完全不做**（不模拟交互） |

**结论**：基础层靠"用真浏览器"即可通过；特征层在 headless 下会部分暴露；
**行为层完全空白**——这正是"约 50%"的来源。

因此优先级应当是：**频率控制（第 2 类）> 指纹伪装（第 5 类）**。
频率是行为的粗粒度，可控；轨迹是细粒度，不做。

### 16.4 软封：最容易骗过判定的拦截形态

温州人才网实测的软封**不是 403**：

| 特征 | 具体值 | 为什么难发现 |
|---|---|---|
| HTTP 状态码 | **200** | 所有"看状态码"的判断全部失效 |
| 响应大小 | **3103 字节**（正常约 83,099） | 只有量级对比才看得出 |
| 页面特征 | 含 `no_page_group` | 站点改模板即失效，只能当旁证 |
| 解析结果 | **0 条** | 与"这页真的是空的"同形 |

**事故记录**：封禁后程序把 200 当正常，继续翻页，**2.5 分钟内又发 53 个请求**，把封禁时间往后推。

**现行为**（`probe_canary()`）：

```
某页解析 0 条
  → 请求 canary_url（已知一定有内容，如 jobtag=147 第 1 页）
  → 两边都 0 条：判 soft_block_suspected，停止 + 写冷却文件 + 报告 failed
  → canary 有卡片：本页确实为空，继续
```

**为什么不用字节阈值**：模板一改就失效。**行为判据（对照页）> 数值判据**。
代价：每触发一次多 1 个请求。

#### 16.5.1 密度 vs 总量（口径修正）

早期表述"某站 150 次请求就被封"把密度说成了总量。正确表述见 16.3 的实测表：
**约束是单位时间密度**（约 21 次/分钟触发），不是单纯累计。

**现行规则**：

```
≤12 次/分钟（实现为 4.8~6.5 秒最小间隔 + 60 秒滑窗 ≤12；单任务 ≤200 请求 / ≤30 分钟）
单任务 ≤200 请求（gate 预算）
单轮 ≤30 分钟（gate 时长）
当天只跑一批
```

兜底两条：
- **连续 3 页 0 条 → 中止**（防选择器写错把整站标成已完成）
- **每页平均卡片数人工核对**：正常 4~5 条/页；若 1~2 条，说明被降级但返回 200，按 partial 处理

### 16.6 明确**没做**的

| 没做 | 原因 |
|---|---|
| 代理池 / 换 IP | 成本 + 性质变化（从"访问"变"对抗"） |
| 随机轮换 UA | 对风控意义有限，制造矛盾指纹 |
| 长尾随机停顿 | 无证据表明降低封禁率；只增加耗时 |
| 全站切 cffi | 三站已切；其余站未逐站验证，不能一刀切 |
| 跨运行保存 Cookie | 仅登录态站有价值，本项目不做登录态 |
| 破验证码 / 绕登录墙 | 性质变化 |
| 逆向签名算法（L3） | 成本高、随版本失效；改用渲染绕开 |

**现状定性**：`identity.py` + 三站 cffi 已把 UA / Sec-CH-UA / TLS 对齐；其余 plain 站仍是“头说 Chrome、握手像 Python”的半套伪装。
在专业风控中，半套伪装可能比诚实自报更可疑——所以对外只说“主力三站已对齐”，不说“全线对齐”。

### 16.7 站点分层与档位

| 层 | 特征 | 取数方式 | 现状 |
|---|---|---|---|
| **L1** 服务端渲染 | 源码里有数据，`?page=N` | 直接抓 HTML | ✅ 已验（wzrc / yqrc / foodlaw / quotes） |
| **L2** JS 渲染 / 明文接口 | 首屏空壳，XHR 取数，无签名 | 渲染；或直接打明文接口 | ✅ 已验（v10：quotes 0→10；api_candidates 可录） |
| **L3a** 签名/加密接口 + 页面可渲染 | 接口带签名或加密载荷，但页面能渲染出数据 | **渲染绕开** 或 **旁听**（只读明文响应） | ✅ **已验**（jrzp 第 1 页，2026-11-14） |
| **L3b** 前端反自动化 | 页面已给，但 JS 自查调试器/CDP，查到自毁 | **拦检测脚本 + 有头** | ⚠️ 可过但留痕 |
| **L3c** 登录墙 | 第 1 页免费，翻页要登录 | 无（没账号） | ❌ **不做**（jrzp 实测） |
| **L4** APP 专用 | 仅客户端 | 抓包 + 证书固定 + 设备指纹 | ❌ 不做 |

档位差异（站点配置；实际都还要过闸门 4.8~6.5s）：练习站 1.2~2.5s；法规站 0.8~1.5s（附件开）；温州系 3~5s（软封检测开、共享冷却组）。
**越像公共大站，档位越保守。**

### 16.8 「用接口能省请求」怎么判（含实测反例）

常见说法：招聘站大量用 XHR/API，一个接口一次返 20~50 条；用 Playwright 监听 `page.on("response")` 找到接口，请求数能从 5000 降到 100~200。

**判断：方向对，但混了两件事，数字不普适。**

**① 拆成两件事**

| 说法 | 实质 | 能省请求吗 |
|---|---|---|
| 用浏览器监听找接口 | **侦察**（一次性） | ❌ 监听本身仍要渲染 |
| 找到后直接打接口 | **稳态抓取** | ✅ 省的是"每页只给 5 条"的浪费 |

正确姿势：**浏览器只用于侦察，之后用 requests 直打**。

**② 本站是反例（实测）**

wzrc 列表为服务端渲染，HTML 直接含 5 条完整职位。
加"每页 50 条"参数后：200 / 86,712 字节 / **仍是 5 条**。
→ **既没有列表接口，也不接受放大页长。**

**③ 四个判断问题**

| # | 问题 | 若答案 | 收益 |
|---|---|---|---|
| 1 | 数据在网页还是接口 | 网页 | 0 |
| 2 | 接口单次条数 | 10~20 | 小~中 |
| 3 | 是否要签名/登录 | 要 | 0（L3，放弃） |
| 4 | 是否仍需逐条详情 | 需要 | ≈0 |

**④ 验证配方（1~3 请求）**

```
1) 源码里有没有完整字段？有 → 不必找接口
2) F12 → Network → 翻页：有无返回数组的请求？带签名/令牌？
3) 复制为命令，去掉 Cookie 重放：仍返数据=可直打；401/签名错=L3 不做
4) 核对：接口单次条数、是否仍需详情、robots 是否允许该路径
```

公式：

```
省不省 =（接口每条数 ÷ 网页每页数）×（1 − 仍需详情比例）×（要不要签名 ? 0 : 1）
```

**⑤ 该说法忽略的风险**：robots 通常只约束网页路径，不写接口路径。
**换接口不等于更合规**——反而可能绕过站点原本的限制意图。接口路径同样要过 robots 判定。

### 16.9 一句话

> 能规避：**频率（实测 + v12 闸门硬约束）、软封（canary）、基础请求头、Cookie 登录态、单页级真浏览器**。
> 不能规避：**API 签名（改用渲染绕开）、验证码（人工过一次）、引擎级强指纹**。
> 护城河不是"绕过所有检测"，而是**选站（L1/L2）、节奏（有数据支撑）、被禁即停并上报**。

### 16.10 jrzp 实测：三道锁与「旁听」（2026-11-14/15）

#### 三道锁与判定证据

| # | 层 | 触发条件 | 响应证据 | 解法 |
|---|---|---|---|---|
| 1 | CDN UA ACL（Tengine） | `headless=True` → UA 含 `HeadlessChrome/157` | `403 denied by UA ACL = blacklist` | `headless=False`（真 Chrome） |
| 2 | disable-devtool | CDP attach（Playwright 必然触发） | 跳 `about:blank`，`page.content()` = **39 字节** | `page.route` abort 其独立 chunk |
| 3 | 登录墙 | 点击第 2 页 | 前端弹登录框（关闭后重点仍弹） | 无账号 → **不可过** |

#### 关键实现（已验证）

```python
page.route("**/*", lambda r: r.abort() if "disable-devtool" in r.request.url else r.continue_())
page.on("response", lambda r: capture(r) if "/zpapi/api/jobs" in r.url else None)
```

实测（有头 + 拦 chunk）：

```

XHR 5 个，全 application/json：

  /areas/28009/children, /jobs
jobs 响应：{"pageNum":1,"pageSize":10,"totalCount":112084,"totalPages":11209,"dataList":[...]}
```

#### 请求加密、响应明文（旁听成立的前提）

```json
POST /zpapi/api/jobs
{"version":"v1","keyId":"v1","timestamp":...,"nonce":"...","iv":"...","cipherText":"...","mac":"..."}
```

请求体 AES-GCM 加密（`nonce+iv+cipherText+mac`），**无法自行构造**；
**但响应是明文 JSON** → 让页面自己发，只读响应，**不解密、不逆 JS**。

#### disable-devtool 的确切配置（自 main-B-uy8eTP.js 抠出）

```js

```

- **独立 chunk**（动态 import），不是内联 → 可路由拦截
- `detectors:'all'` → CDP 一挂即触发

### 17.2 关键一步：`published` 有三种形态，不能混

这是整件事**唯一容易做错**的地方：

| 形态 | 例子 | 正确处理 | 错误处理 |
|---|---|---|---|
| 绝对日期 | `2026-06-09` | 解析成日期算 age | — |
| **相对时间** | `2小时前` / `3天前` | **N天前=age N；N小时前=age 0** | 当成"未知"（错，它们是最新的） |
| 空 | `""` | 才进"日期缺失"桶 | — |

**基准日必须写死**（本次用 `2026-11-11`），不能用 `now()`——否则明天再跑一遍结果就变了，无法复现。

## 十八、没有网址时，怎么找到目标站（2026-11-14 重写 · 通用版）

> 这一章回答一个问题：**只告诉我"我要什么数据"，不给网址，我按什么顺序找、按什么标准判断值不值得接。**
> 适用于任何领域（招聘 / 法规 / 价格 / 天气 / 招投标…），不再只服务招聘。
> 判据编号（F-01 … F-22）可被规则框架直接引用。

---

### 18.0 适用范围

```
输入：一个目标（"爬浙江招聘站""要国家法规全文""要某商品历史价格"）
输出：候选源清单 + 每个源的评分 + 建议的抓取方式
不含：具体解析规则（那是站点适配层的事）
```

---

### 18.0.1 先判型：不是每个目标都要“找站”（2026-11-15 补）

> **这一节是总闸：先判 A/B/C/D，再决定要不要搜索、要不要跑六步。**
> 判错型，后面每一步都是白干。
>
> 配套通用框架：`框架-数据源优先级-通用-20261114.md` 第〇节。

| 型 | 判据（一句话） | 需要几个源 | 停止条件 | 典型 |
|---|---|---|---|---|
| **A 单点权威** | 这条数据只有一个机构在产生 | **1~2** | 找到那个机构就停，**不进 ②~⑤** | 天气、国家法规、汇率、统计年鉴 |
| **B 多源长尾** | 数据由成千上万个主体各自发布 | 10~50+ | 跑六步，按覆盖度停 | 招聘、租房、二手、招投标、本地服务 |
| **C 账号在环** | 数据在平台内，而你已经有账号 | **1（你的账号）** | **先问账号，再谈发现** | 拼多多价格、知乎、微博、小红书 |
| **D 开放 API** | 别人已经把数据做成接口了 | **1** | 直接调接口，**不抓页面** | 天气 API、汇率、开放数据平台 |

判型三问：

```text
① 这条数据是谁“产生”的？          一个机构 -> A/D；无数主体 -> B
② 我手上有没有账号？              有，且数据在平台里 -> C
③ 有没有现成接口？                有 -> D（连抓都不用抓）
```

**结论：六步发现不是“流程”，是“多源任务的搜索策略”。**

```text
天气 —— A/D 型：中央气象台或天气 API，1 个源，找到就停
法规 —— A 型：国务院 / 司法部 / 地方公报，最多 1~3 个官方源
价格 —— C 型：你手上有拼多多账号，账号就是源；先问账号，不找站
招聘 —— B 型：才需要搜索 + 六步发现
```

> **代码现状（2026-11-15）**：`discover.py --mode` 已提供 `single / wide / account`，
> `--goal` 已改为所有模式必填；`weather/regulation + wide` 会被拒绝，必须显式 `--force-wide` 才放行。
> 调用者仍必须先判型；不能靠默认值。

---

### 18.1 通用决策框架：4 个维度，不是固定顺序

任何领域，先给每个候选源打 4 个 1~5 分：

| 维度 | 问什么 | 低分长什么样 |
|---|---|---|
| **适配度** | 这条数据直接回答我的问题吗？ | 只是相关，不是要的字段 |
| **时效性** | 更新频率够我用吗？ | 一季度一更，而我要日更 |
| **可得性** | 公开吗？SSR/接口？要登录吗？反爬吗？ | 要付费账号 / 强 WAF |
| **权威性** | 一手发布还是二手转述？ | 自媒体转述、无出处 |

**排序 = 适配 × 时效 × 可得**；权威性作为**质量标签**，不参与排序。

为什么权威性不参与排序：政府招聘公告最权威，但对求职者适配度低（考试流程、竞争比高），所以排最后。**权威 ≠ 该先抓。**

---

### 18.2 五个来源层（顺序会随领域翻转）

```
① 一手发布者   —— 谁第一个产生这条数据
② 行业垂直     —— 该行业的门户/协会/数据库
③ 通用平台     —— 大平台、城市站、电商
④ 聚合/索引    —— 搜索引擎、目录站、比价站
⑤ 二手转述     —— 自媒体、百科、论坛（只作线索）
```

同样五层，四个领域排序完全不同：

| 领域 | 一手 | 垂直 | 平台/接口 | 结果排序 |
|---|---|---|---|---|
| **招聘** | 企业官网 | 行业站（食品伙伴网） | 城市人才网、综合平台 | 企业 → 城市网 → 政府 |
| **法规** | 国务院/司法部/地方公报 | 北大法宝（付费） | 搜索引擎、法律门户 | **一手 → 聚合 → 垂直** |
| **商品价格** | 交易所、统计局、商家官网 | 生意社（付费） | 电商平台 | 看需求：行情→交易所；零售→垂直/比价 API |
| **天气** | 中央气象台 | 天气门户 | **和风/彩云 API** | **API → 一手 → 聚合** |

**结论：没有万能顺序，只有万能尺子。**

### 18.3 招聘实例（已定稿，作为第一个实例保留）

```
第 1 类 企业社招
      a) 行业垂直招聘站（该行业门户的招聘频道）
      b) 行业头部企业官网（先本地龙头，再全国大厂 —— 见下方「本地优先」）
      c) 招聘平台的公司定向页（需本人账号，白名单 + 低频，属 v15）
第 2 类 城市网站招聘
      先一线/新一线（杭州、宁波、南京、苏州），再二线
      默认不下沉到县级；除非范围明确给到"市"
第 3 类 政府 / 官方
      事业单位统考、公告；低频、有考试流程，作补充
```

预算参考：第 1 类 60% / 第 2 类 30% / 第 3 类 10%。

**本地优先（2026-11-14 实测，样本 n=3，仅食品行业）**：这三家全国巨头的岗位跟着总部和主工厂走。
双汇（河南）+ 蒙牛（内蒙）274 条，**浙江+江苏只有 6 条（2.2%），食品检测岗 0 条**；伊利 1,410 条约 4.5%（抽样 110 条外推）。
所以第 1 类 b) 的**建议**顺序是：**本地龙头 → 有本地实体的全国大厂 → 全国大厂**。
判据（F-21）：这家公司的岗位有多少落在目标城市？
**注意样本边界**：只验过 3 家、且全是食品；互联网/制造/金融、其他省份都没验，不许当成普遍规律。

### 18.4 找站的技术路径（仅 B 型或 A/D 型尚未定位一手源时使用）

> **适用前提**：只有 B 型（多源长尾），或 A/D 型但还不知道一手源是谁时，才进入本节。
> A/D 型已知官方站/API、C 型已有账号 → **不进入“找站”流程，更不跑六步**。
>
> 在“确实需要找站”的前提下，检索通常是最便宜、召回最高的第一步；
> 但检索不是所有任务的强制第一步。原「顺序不能反」作废，不等于「检索永远第一」。

| 路径 | 成本 | 做法 | 适用 |
|---|---|---|---|
| **⓪ 检索** | **1 次搜索** | 按 `tools/geo/search_queries.json` 的模板（{省}/{市}/{行业}）× 地区，产出候选域名。**没有候选源/不知道一手源时才先用它** | B 型；A/D 型尚未定位一手源 |
| **① 官方名录** | **0 请求** | 读 `tools/geo/gov_platforms.json`；或抓主管部门的名单页 | 政府/事业单位/官方平台（招不到在商业站页脚） |
| ② 页脚/友链 | 0~2 请求 | 抓一个已知站首页，按出现次数排外链域名 | 同类站互挂友链的领域 |
| ③ 域名语法 + DNS | **0 HTTP** | 按命名规律生成候选（`{city}rc.com` / `wz{abbr}rc.com` / **`{省}hr.com`**），批量解析 | 站群型平台 |
| ④ 平台指纹 | 0~1 请求/站 | 第三方资源域名、robots MD5、favicon 字节 | 判断"是不是同一家" |
| ⑤ 明文接口 | 1~2 请求 | 从页面 `script` 的 `url` + `queryData`、或 XHR 日志里找接口 | 列表是 JS 渲染的站 |

**推论（写死）**：凡是"猜域名能解决"的，都不是真问题；**猜不出来的那一类，才是发现阶段真正的洞。**

#### 18.4.0 判据 F-22：检索优先（有条件，2026-11-15 补）

| 编号 | 判据 | 怎么取 | 阈值 |
|---|---|---|---|
| **F-22** | 检索优先（有条件） | **需要找站**且没有候选源时，先跑 3~5 条检索模板，再进入域名生成；找"某类官方平台"时先找主管部门名单页。A/D/C 型已知源/账号时不检索 | 一次发现里检索条数 = 0 且未说明原因 → 判漏项；不需要找站却强行检索 → 判浪费 |

**边界**：F-22 只约束“需要找站”的 B 型，以及尚未定位一手源的 A/D 型；已知源/账号的 A/D/C 不检索。

**反例（2026-11-14，B 型/未知源的发现阶段，有完整产物可复核）**：

```
v13 的发现阶段只有四条"向内看"的路（页脚 / 域名语法 / 友链 / 人工 seed），
244 个候选里 A 档 16 个往下走、B 档 98 个全丢，结果漏掉两个省级官方平台：

  zjrc.com    浙江人力资源大市场 —— 被枚举出来了，但 "zj" 被判成「镇江」，判 B 档扔掉
  zjhr.com    浙江省公共就业服务平台 —— 5 种后缀模板全带城市名，没有 {省}hr 这一档，它根本生成不出来
  js365job.com 江苏"就在江苏"智慧就业服务平台 —— 244 个候选里压根没有
```

**正例（2026-11-15 实测）**：

```
1 个请求 → http://job.mohrss.gov.cn/jy/index.jhtml 《各省公共就业服务平台》
          = 32 条省级平台直链（31 省 + 兵团），其中就含 www.zjhr.com 与 www.js365job.com
          （该页用图片当锚文本，必须从 href 抽，按可见文字抽只能捞到 2 条）

1 次检索 → 江苏"就在江苏" + 山东省公共就业人才服务网上服务大厅（2024-09 改版的新域名），
          都是先搜到官方公告、才拿到现用域名的
```

**两条长期规则（取代"顺序不能反"）**：

```
规则一  需要找站时，先「检索」，不是先「猜域名」。
        已经知道一手源/接口时，直接停，不需要为了“流程完整”再搜一次。
规则二  找某类官方源，先找「主管部门的名单页」，再谈逐家搜。
        —— 1 个请求拿全国省级平台，比搜 31 次更省也更权威。
```

#### 18.4.1 检索结果不许直接信（血的教训）

```
搜到 ≠ 能用。检索结果里混着：跨省的站、第三方聚合站、高校公告页、已改版的旧域名。
规则：检索只产出"候选"，必须 1 请求验（title / 岗位链接 / robots）才算数。

同理，名单页也会过期：人社部那份名单里第 6 位是 IP 直链 111.41.62.147:13332，
2026-11-15 实测 ConnectionReset（已下线）。名单只保证"曾经存在"。
```

#### 18.4.2 「官方」不等于「好抓」，也不等于「全省均衡」

```
2026-11-15 抽样 11 个省（每个 1 请求）：
  SSR 有内容、值得接      3 个   吉林 jlrc.com.cn（327 KB / 可见 1 万字） 四川 sc91.org.cn 陕西 qinyunjiuye.cn（半 SSR）
  SPA 空壳（要挖接口）     6 个   辽宁 / 福建 / 贵州 / 新疆 / 上海 / 广东 / 湖南 / 云南 / 甘肃（后 4 个为 11-14 抽样）
  打不开或停放            2 个   河南 hn91w.com 超时；黑龙江 4 个候选全失败（job.hlj.gov.cn 超时、hljjob.com 是域名停放页）
  极少数是老 JSP          1 个   浙江 zjhr.com —— 明文 POST 接口，零门槛（但台州占 97%，见 F-21）
```

**名录里必须允许"没有统一平台"这一状态**（字段 `coverage`）：

```
coverage: unified     该省有省级统一入口（能从人社部名单直接拿到）
          fragmented  多线并存、没有单一入口（如江苏：js365job + 省人才服务云）
          unknown     未查明（如黑龙江、河南）
—— 宁写 fragmented/unknown，不硬凑一个域名。
```

**注（2026-11-15）**：旧版把页脚/域名/指纹/接口编成 ①~④，现在重新编号为 ②~⑤，
⓪ 检索 与 ① 官方名录 插到最前。路径本身没变，变的是**顺序和优先级**。

### 18.5 判据清单（F-01 … F-22）

### 可达性与意图

| 编号 | 判据 | 怎么取 | 不满足 |
|---|---|---|---|
| **F-01** | robots 可读 | `GET /robots.txt`，200/404 都可继续；403/5xx 视为拒绝 | 停，标 `blocked` |
| **F-02** | robots 决策 | 按 UA 分组 + 最长匹配 + `*`/`$`，取命中规则行号 | 禁 → 停，留痕 |
| **F-07** | WAF 特征 | ① `home` 与 `robots.txt` 同 MD5 ② 含 `aliyun_waf_*` meta ③ 200 但正文 <300 字 | 判 `blocked`，**不绕过** |

### 内容判定

| 编号 | 判据 | 怎么取 | 阈值 |
|---|---|---|---|
| **F-03** | 可见正文长度 | 去标签后正文字数（不是字节数） | <300 字 → 空壳/需渲染 |
| **F-04** | 领域关键词 | `<title>` + 正文命中领域词 | 命中 ≥2 才算相关 |
| **F-05** | 每页条数 | 列表页同构条目 | <3 条 → 结构异常 |
| **F-06** | 总页数 | `count` 字段或"共 N 页" | **只作参考**，终止条件见 F-18 |
| **F-21** | 地理重叠度 | 抽样看该源数据的地区分布 vs 目标地区 | **重叠 <5% → 该源降级** |
| **F-22** | 检索优先（有条件） | 需要找站且没有候选源时先跑 3~5 条检索模板；找官方平台先找主管部门名单页；已知源/账号时不检索 | 检索条数 0 且无说明 → 判漏项；不需要找站却强行检索 → 判浪费 |

### 形态判定

| 编号 | 判据 | 怎么取 | 结论 |
|---|---|---|---|
| **F-08** | 列表形态 | 列表页正文长度 + 是否含条目 | SSR / SPA / 接口 |
| **F-09** | 接口线索 | `script` 标签的 `url` + `queryData`；页面内 `.json`/`ajax`/`fetch(` | 有 → 直接调接口，**跳过渲染** |

### 平台与皮肤

| 编号 | 判据 | 怎么取 | 结论 |
|---|---|---|---|
| **F-10** | 平台指纹 | 第三方资源域名及出现次数（如 `img.jrzp.com` ≥20） | 判"哪一家" |
| **F-11** | 同部署 | robots.txt 字节完全相同（MD5） | 同部署（白送的一票） |
| **F-12** | 同图标 | favicon 字节完全相同 | 同代皮肤 |
| **F-13** | 皮肤代 | 静态路径数 + favicon | A 代（≥120 路径、同图标）可批量；B 代单独适配 |

### 结构与同库

| 编号 | 判据 | 怎么取 | 结论 |
|---|---|---|---|
| **F-14** | 类目/地区识别 | **锚文本**（"杭州人才网""食品检测"），不是域名拼音 | 命名风格不统一时唯一可靠办法 |
| **F-15** | 域名召回 | 用已知答案校验生成器 | 召回不足则不许拿去枚举新地区 |
| **F-16** | IP 用法 | 解析 **www**（apex 常为停放页）；IP 会轮转 | 只作辅助证据，不跨时间比较 |
| **F-17** | 同库 | L1 指纹 / L2 结构 / L3 数据（抽 10 条回查） | ≥9/10 同库；3~8 部分共享；≤3 独立 |

### 工程约束

| 编号 | 判据 | 说明 |
|---|---|---|
| **F-18** | 终止条件 | **不信 count**：翻到本页 0 条或与上页重复才停（实测 131 vs 实际 141） |
| **F-19** | 编码 | 先看响应头/meta；政府与行业站常见 GBK/GB2312，按 UTF-8 读会变成乱码 |
| **F-20** | 预算 | 每任务 ≤200 请求；发现阶段 ≤30；渲染按子资源单独设上限 |

### 18.6 形态三态与对应策略

| 形态 | 特征 | 策略 | 成本 |
|---|---|---|---|
| **SSR** | 列表页正文完整 | 直接抓，写 `parse_list` | 1 请求/页 |
| **接口** | 页面里有 `url`+`queryData` 或 XHR | 直接调接口（JSON/HTML 片段） | 1 请求/页 |
| **SPA** | 列表页是空壳 | ①先找接口 ②没有才渲染（v14 T2） | 渲染 ≈ 10~20 倍负载 |
| **SPA + 反自动化**（2026-11-14 新增） | 渲染后页面**自己跳成 `about:blank`**、或弹验证 | **放弃，不绕过**（判据：html <200 字节 且 final_url=about:blank → `page_self_destructed`） | — |

**优先级永远是：SSR > 接口 > 渲染 > 放弃。** 渲染是最后手段，不是首选。

> **实测（2026-11-14）**：jrzp 系列表页在 headless 与 headed 两条通道下**都会自毁**（console.clear + 跳 about:blank），
> 因此 jrzp 从 `needs_v14` 改为 **`blocked`**（`transport=none`），只保留首页 SSR 热门块。
> **教训：「等 v14 就能吃 jrzp 300 城」这个判断是错的**——有些站的反自动化不在签名层，而在页面自毁层。

### 18.7 平台与皮肤：决定"能不能批量"

```
平台（F-10）：这站是谁家的 —— 决定能否复用适配器
皮肤（F-13）：这站用哪一代模板 —— 决定复用后要不要改解析
```

实测：同一平台 7 个城市站 robots 完全相同，但分成 A/B 两代皮肤，**Jaccard 0.05 vs 0.78**。
→ 判平台只用平台证据；判能否批量必须再看皮肤。**把两者混成一个"同模板"，会在 B 代站上全线解析失败。**

### 18.8 同库判定（沿用三级协议）

```
L1 指纹   0 请求   平台/皮肤/商标/版权
L2 结构   1~2 请求 分站声明页数 vs 主站该地区子集
L3 数据   2~3 请求 抽 10 条按「id + 公司 + 岗位 + 时间」回查
```

台账必须写样本量：
```
✓ verified: L3, n=10, 2026-11-12, id 命中 10/10 → 同库（74cms 温州系）
✗ verified: 同库                      ← 不合格写法
```

#### 18.8.1 L3 的实测边界（2026-11-14 补）

| 站对 | L1 指纹 | L2 结构 | L3 数据 | 结论 |
|---|---|---|---|---|
| 温州 wzrc 主站 ↔ 区县分站（74cms） | 同 | 同 | **n=10，id 命中 10/10** | **同库** ✅ |
| 苍南 cangnanrc ↔ 瓯海 wzohrc（jrzp） | 同（`img.jrzp.com`、robots MD5、favicon） | 同（Jaccard 0.776，同名 74%） | **做不了**：双方列表/详情都是 SPA，取不到详情页 | **只能判到 L2** ⚠️ |
| 北森 双汇 ↔ 蒙牛 | 同平台（不同租户） | 不同（Skin/内容不同） | 不需要（不同公司） | 独立租户 |

jrzp 站对那行的实测细节（2026-11-14，3 请求）：

```
· 苍南首页 job id 123 个 / 瓯海 125 个 → 交集 0
· 抽 3 个苍南 id 去瓯海 /job{id}.shtml → 全部 200 但只有 389 字节（空响应）
· 但两站首页岗位标题交集 81/110（74%）
→ 内容高度重叠，id 空间不通用，交叉验证拿不到详情 → 结论只能是"疑似同库，L3 未验"
```

**这条要记进方法论**：L3 的前提是"双方都能取到同一个岗位的详情"。SPA 站群做不到，
所以对 SPA 站群只能声明 **L1/L2 已验、L3 未验**，不许写"同库"。

### 18.9 Rule 0：不碰清单

以下任一成立 → **立即停，不升级手段，报给用户**：

```
· robots 禁止该路径
· 出现验证码 / 人机验证
· 出现商业 WAF 挑战页（aliyun_waf / 站点所有路径返回同一页）
· 需要登录才能看的非公开数据（除非用户明确授权本人账号）
```

自动识别特征见 F-07。**"技术上能做"不等于"可以做"。**

### 18.10 能力边界（2026-11-14 版）

1. **搜索引擎对县级站基本失效**——不能当主力，只能兜底。
2. **没有种子时命中率下降**，但已大幅缓解：一个省级站页脚就能给出全国 22 个省站。
3. **层级判定是启发式**——首页像什么不代表列表页是什么，必须探列表页。
4. **`count` 字段不可信**，分页必须翻到空页为止。
5. **IP 不稳定**：apex 多为停放页、IP 会轮转，只能作辅助。
6. **覆盖仍不完整**：能找到的是"有公开索引/有友链/有语法规律"的站，找不到的是纯线下或强封闭的站。
7. **全国性大厂的岗位集中在总部 / 主工厂**：双汇 + 蒙牛 274 条里，浙江 + 江苏只有 6 条。地方求职应优先本地公司，而不是名气最大的公司。

### 18.11 一句话

> 不是"我会自动找到所有站"，而是"**给我一个种子，我能顺着友链、域名语法、平台指纹、明文接口四条路，把一个地区或一个行业的站捞出来，并用 F-01~F-20 判断每个站值不值得接**"。
> 换领域时，尺子不变，答案重算。

## 十九、v12 请求闸门与两段式（2026-11-13，实现口径）

### 19.1 为什么要有它

之前的「≤10 次/分钟、单任务 ≤150」写在文档与技能里，但**引擎一行代码都没实现**——
全靠每次手工传 `--delay 5 7`。忘一次就回到 24~50 次/分钟（当时默认 1.2~2.5 秒、**还没有闸门**），
对被封过的站基本等于 5~6 分钟进冷却。这是"文档承诺 > 代码能力"的典型。

v12 把它变成机制：

```
crawlers/gate.py   RequestGate
  · 最小间隔 uniform(4.8, 6.5) 秒     ← 主节流 + 主抖动
  · 滑动窗口 60 秒 ≤ 12 次            ← 天花板（正常跑约 10.6 次/分，很少触顶）
  · 单任务 ≤ 200 个请求               ← 先判后加：第 200 个放行、第 201 个抛
  · 单轮 ≤ 1800 秒                   ← 第 1 个请求（robots）总是放行
  · now_fn / sleep_fn 可注入          ← 测试用假时钟，不 sleep、不 flaky
```

**钩子位置**：`Session.send()`，不是 `request()`。
原因：列表/详情请求是 `allow_redirects=True`，重定向走 `send()`；挂 `request()` 会漏掉每一次 302 跳转。

**回环豁免**：只有存在 `CRAWLER_TEST_TMP / CRAWLER_OUT_DIR / CRAWLER_LOG_DIR` 等变量时才豁免 `127.0.0.1`；
生产即使目标是回环也走闸门（`CRAWLER_GATE_FORCE=1` 可强制开启，测试用它证明"回环也生效"）。

**报告新增**：

```json
"gate": { "max_rpm": 12, "max_requests": 200, "max_seconds": 1800,
          "requests_used": 11, "elapsed_sec": 96, "actual_rpm": 6.9,
          "throttled": 6, "stopped_by": "", "by_host": {"www.wzrc.net": {...}} }
```

### 19.2 四个阶段的闸门穿透（v12.1）

闸门可能在**详情 / 附件 / canary / 补抓**任一阶段触发。之前的 `except Exception` 会把它吞成"这一条失败"，
然后继续跑到预算之外。现在的规则：

| 阶段 | 停止时 | 用例 |
|---|---|---|
| 详情 | 本页列表数据**先落盘**（不标断点，靠 `seen_keys` 去重）；未抓的详情标 `detail_fetch=skipped_budget`（进可重试集合） | 190 |
| 附件 | 记录先落盘；未下的附件标 `status=skipped_budget`；`skipped_budget` 同时进 `ATTACH_RETRY_STATES` | 191 |
| canary | 按"无法判定"处理，**不抛 traceback** | 192 |
| 补抓 | 半途收工，文件原状态保留 → 下次续跑 | 193 |

`finalize` 顺序：**闸门原因优先于"详情待补"**（根因 vs 后果），报告写 `request_budget_exceeded`，
不会被 `detail_pending_remains` 盖住。

### 19.3 附件状态必须"边下边记"（v12.1）

原来 `download_attachments` 是"全下完再 `row["attachments"] = out`"。
闸门中途停止 → `out` 丢掉 → **已下好的文件状态消失**、记录退回原始字符串（文件成孤儿）。

改成：进循环前把 `row["attachments"]` 换成 dict 列表（`status` 留空），每个文件**原地更新**。
用例 191 断言精确值：**7 个附件 = 2 ok + 5 skipped_budget**。

### 19.4 两段式（v12.2 骨架 / v12.3 补齐）

```
① crawler.py --site X --job J --detail-mode off          # 只抓列表
② tools/pick_details.py --job J --keyword … --only-pending --out cand.txt   # 0 请求
③ crawler.py --site X --job J --detail-urls cand.txt     # 只抓清单里的详情（+ 选中记录的附件）
```

| 口径 | 期望 | 含义 |
|---|---|---|
| `stats.pages_total` | **0** | 第 2 段不发列表请求 |
| `datafile.records_before_run` | **== total_after_run** | 只补字段，不改行数 |
| `datafile.records_new_this_run` | **0** | 不是新增 |
| 详情成功 | `success / details_repaired` | doctor 认这个 reason |
| 附件有失败 | **`partial / attachment_partial`**（rc=3） | 不假装补好了 |
| 清单为空 | `failed / detail_urls_empty` | 账目仍自洽（用例 200） |
| 清单含数据外 URL | 计数 `detail_urls_missing` | 不崩（196） |
| 站点无 `parse_detail` | `failed / detail_urls_no_parser` | 显式拒绝（如 wzrc_all） |

**关键实现细节**：`--detail-urls` 模式下必须**跳过例行详情/附件补抓**，
否则"只抓清单"会被前面的自动补抓变成"全补一遍"（第一版就踩了：`planned=3`）。

**doctor 兼容**（v12.3）：
- success 的合法 reason 扩为 `{ok, details_repaired}`；
- repair-only 运行时（两段式第 2 段 / 补抓 / 补附件）`卡片密度` 判 **`PASS 不适用`**，不再 WARN。
